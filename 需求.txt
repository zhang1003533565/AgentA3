2. 数据库变更（JPA 实体驱动）【✅ 已完成】
说明：本项目使用 Spring Data JPA + hibernate.ddl-auto=update，表结构由 @Entity 实体自动创建/补列，sql.init.mode=never（不会执行手写 DDL）。因此下列 SQL 仅作为字段设计参考，实际以新增 JPA 实体 + JpaRepository 实现；创建/更新时间使用 @PrePersist/@PreUpdate（与现有实体一致），无需依赖数据库 DEFAULT/ON UPDATE。

2.1 新建：课程资料池表（campus_course_material）【✅ 已完成 — CampusCourseMaterial.java】

sql
CREATE TABLE campus_course_material (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    course_id BIGINT NOT NULL COMMENT '所属课程ID',
    file_name VARCHAR(255) NOT NULL COMMENT '原始文件名',
    file_url VARCHAR(500) NOT NULL COMMENT '存储路径（COS或本地相对路径）',
    file_size BIGINT NOT NULL COMMENT '文件字节大小',
    file_type VARCHAR(20) NOT NULL COMMENT '扩展名（mp4/pdf/ppt等）',
    mime_type VARCHAR(50),
    duration_seconds INT DEFAULT 0 COMMENT '视频/音频总时长（秒），文档可存总页数；默认0表示不做自动完成判定（见 3.3 两阶段说明）',
    deleted TINYINT DEFAULT 0 COMMENT '软删除标记：0-正常 1-已下架（保留文件与 URL）',
    upload_batch_id VARCHAR(64) COMMENT '批次ID，用于追踪同一文件夹上传的文件',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_course_id (course_id)
);

3.1 文件夹上传与预检接口（高性能）【✅ 已完成 — AdminMaterialController.folderUpload + CourseMaterialService】

POST /api/admin/materials/folder/upload

入参：courseId，List<MultipartFile> files（前端平铺传递文件夹内文件）。

核心逻辑：

类型检索（白名单）：仅允许 mp4, avi, pdf, ppt, pptx, doc, docx, xls, xlsx, png, jpg, jpeg, gif, webp, mp3, txt。如果包含不在白名单的文件，立即抛出异常并提示具体文件名，拒绝整个文件夹上传。

总大小约束：累加所有文件大小，超过 2GB 则抛出异常拒绝上传。

存储：校验通过后，遍历文件，调用新建的 FileStorageService.store() 方法保存（本地/COS 双模式，独立实现，不改动 UploadController），并批量写入 campus_course_material 表。生成一个随机的 upload_batch_id 标记本次批次。

请求体积说明：application.yml 当前 multipart.max-request-size=200MB。2GB 上限指同一文件夹（同一 upload_batch_id）的累计大小，需前端分批上传、后端按 upload_batch_id 跨请求累加校验；单批请求体须小于 multipart 上限。上限与白名单配置化（见第 6 节）。

3.2 资料引用检查（安全删除）【✅ 已完成 — checkReference / delete】

GET /api/admin/materials/{id}/check

逻辑：查询所有章节的 material_ids 字段（JSON数组），判断该 id 是否被引用。返回被引用的章节名称列表。

DELETE /api/admin/materials/{id}

逻辑（默认软删除）：先调用检查逻辑；若有引用，前端强制确认后，后端遍历所有章节将 material_ids 中的该 ID 剔除（Jackson 过滤），再将该资料 deleted 置为 1（软删除，保留文件与 URL），被引用章节仍可查看并提示“资料已下架”。物理删除文件（或调用 COS 删除接口，不可逆）仅作为管理员二次确认后的可选强操作，默认不执行。

3.3 精细化进度上报与查询（不与旧打卡冲突）【✅ 已完成 — MaterialProgressService】

POST /api/app/progress/material/report：接收 materialId 和 watchSeconds，更新 learning_material_progress 表（累加或更新）。
时长来源分两阶段：第一阶段（当前版本）duration_seconds 默认 0，表示不做自动完成判定，仅累加 watch_seconds，完成状态靠用户手动打卡；第二阶段（待扩展）再解析元数据——PDF/Office 页数可用项目已内置的 PDFBox/POI 解析，视频/音频时长需另引入 ffmpeg 或 Apache Tika，届时当 watch_seconds ≥ duration_seconds 时自动将 status 置为 2。

GET /api/app/progress/course/{courseId}：查询当前用户在该课程下所有资料的进度，并解析各章节 material_ids 一并返回资料列表（每条含 name/url/type/duration_seconds，过滤 deleted=1 的资料），聚合计算章节级进度（章节内资料完成数/总资料数）和课程总进度。
双数据源适配：旧接口 GET /api/app/campus-courses/{courseId} 仍只读 resource_url，保持不动以向后兼容；小程序新版详情/进度 UI 统一改用本新接口获取“资料列表 + 精细进度”，从而单一数据源、避免与旧 resource_url 冲突，也无需 AOP 侵入旧返回体。
关键：当检测到某章节所有资料完成时，由新 Service 注入并直接调用 CampusCourseService.updateProgress(courseId, chapterId, userId, true)（而非后端自调 HTTP 接口，规避 JWT 鉴权与循环调用问题），将旧表 completed 置为 true，确保旧逻辑流转；此处仅调用他人 Service 的现有方法，不修改其内部实现。
