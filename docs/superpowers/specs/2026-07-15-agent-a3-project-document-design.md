## 2. 目标与成功标准

本设计用于生成《AgentA3 智慧校园个性化学习多智能体系统——需求、设计与开发说明书》。成品应在参考文档的正式软件说明书风格上，补齐其缺失的文档治理、需求追踪、接口契约、测试证据、敏感信息管理和事实边界。

成品成功标准如下：

1. 文档总长控制在 70–78 页，A4 纵向。
2. 需求、总体设计、详细设计、核心技术、数据与接口、页面、测试、部署、使用和总结内容完整。
3. 所有功能结论均可由当前仓库代码、配置、设计文档或测试报告支撑。
4. 未实现、未集成或未实测能力必须明确标记为限制或后续规划，不得写成现状成果。
5. 图、表、章节、需求和测试编号连续且可追踪，不得遗留占位符。
6. DOCX 必须经过逐页渲染检查；PDF 必须逐页检查裁切、重叠、字体、表格、页眉页脚和图注。
7. 最终文档不得包含真实密钥、令牌、密码、公网 IP、个人隐私数据或内部绝对文件路径。

## 3. 内容定位

文档主线为“证据驱动的个性化学习闭环”，而非罗列智慧校园的全部功能。校园服务模块作为学习行为来源、业务完整性和落地场景支撑；答辩赛题相关的画像、多智能体、资源、会议、知识库、题库、组卷和考试是正文重点。

核心定位：

> 系统将学生的对话、研讨和资源互动转化为可追溯证据，再由 Leader 编排专业智能体，为不同学生生成并推送不同的学习资源。

## 4. 事实来源与优先级

1. 当前工作树中的生产代码与配置。

5. 参考 PDF 仅作为结构和视觉参考，不作为 AgentA3 功能事实来源。

当 README、历史设计与当前代码冲突时，以当前代码为准。典型冲突包括智能体数量、Python 本地 RAG、考试画像联动和部署边界。

## 7. 章节内容设计

### 7.1 前置材料

- 封面：赛题全称、项目全称、团队名称、版本和日期。
- 文档信息：用途、范围、读者和保密说明。
- 修订记录：V1.0 初版，2026-07-15，AgentA3 项目组。
- 摘要：用一页概括业务问题、解决方案、关键创新和技术架构。
- 目录与图表目录：使用 Word 原生标题层级和自动目录字段。

### 7.2 第一章 项目概述

- 高等教育个性化学习问题。
- 中国软件杯 A3 赛题目标。
- 项目建设目标、边界和预期价值。
- 文档范围、术语和缩略语。

### 7.3 第二章 需求分析

- 用户角色：学生、教师、管理员、商户。
- 业务痛点：入口分散、通用 AI 缺少学习背景、过程信号分散、内容不可追溯、教学资源生产链长。
- 竞品对比：通用聊天机器人、传统教学平台、基础知识库问答与 AgentA3 的架构能力对比；必须注明为能力比较而非统一数据集实验。
- 功能需求：身份、校园服务、学习服务、AI 助手、画像、会议、知识库、题库试卷、考试和 AI 运维。
- 非功能需求：交互、可用性、可靠性、安全、可扩展性、兼容性和可观测性。
- 建立 `FR-*`、`NFR-*` 编号和验收标准。

### 7.4 第三章 总体设计

- 系统上下文：移动端、Web 管理端、Java 后端、Python AI 服务和外部服务。
- 四部分总体架构：uni-app、React/Vite、Spring Boot、FastAPI。
- 组件职责：Java 管业务与治理，Python 管模型调用和智能体执行。
- 数据流：认证、SSE、WebSocket、REST、MaxKB、MySQL、Redis。
- 部署边界：Docker/Compose 当前覆盖 MySQL、Redis、Java 与 Web；Python AI 服务单独启动。
- 安全边界：Python `/internal/*` 为内网服务，不描述为独立公网 API。

### 7.5 第四章 详细功能设计

正文重点模块：

1. 统一身份与角色权限。
2. AI Leader 学习助手。
3. 七维画像雷达与证据更新。
4. 多模态资源生成、展示、互动和导出。
5. 会议预约、实时转写和会后分析。
6. MaxKB 知识库管理与引用式问答。
7. AI 题目生成、结构审查和人工导入。
8. 随机/手工组卷、真实预览证明和 DOCX 下载。
9. 移动端在线考试、自动保存、交卷和客观题评分。
10. 模型、智能体、知识库和系统配置管理。
11. 校园服务域概览。

每个原子功能统一描述：

- 目标与价值。
- 参与角色和权限。
- 触发与前置条件。
- 主流程、替代流程和异常流程。
- 后置状态和业务规则。
- 涉及接口和数据实体。
- 验收条件和对应测试编号。
- 必要时附业务流程图。

### 7.6 第五章 核心技术设计

按以下顺序展开：

1. 七维画像证据协议：维度、证据来源、候选状态、可靠度、冲突和慢更新。
2. Leader 与 30 个专业智能体：Catalog、动态加载、模型绑定、工具白名单和失败策略。
3. 讯飞实时语音转写：JWT 握手、PCM 帧、HMAC 签名、partial/final 文本和发言人广播。
4. 会后智能体链：转写整理、总结、会议控制、成员分析、资源推荐和画像证据。
5. MaxKB 可信问答：命中测试、证据片段、上下文裁剪、来源展示和资料不足拒答。
6. 多模态资源协议：资源类型、来源、证据链、grounding 状态、integrity 和导出。
7. 题库与试卷可信链路：严格 JSON、题型规则、人工预览、一次性预览证明和最终输出一致性。
8. 在线考试一致性：试卷快照、答案版本、自动保存、到期交卷和客观题评分。

每项核心技术统一包含问题与约束、当前实现、输入输出契约、状态机或流程、失败降级、安全与性能边界、验证证据和已知限制。

### 7.7 第六章 数据与接口设计

- 项目当前有 62 个 JPA 实体、61 个唯一映射表。
- 正文详细描述 AI 会话、画像、会议、题库、试卷和在线考试相关关键表。
- 其他校园业务表按身份配置、活动论坛、地图课表、餐饮优惠、二手聊天等领域汇总。
- 明确逻辑关系与物理外键的区别，不宣称所有 ID 关系均具有数据库外键。
- REST API 按领域说明，不在正文逐条抄写 338 个映射。
- 关键接口提供方法、路径、权限、请求、响应、状态、异常和幂等性说明。
- 补充 SSE 事件、WebSocket 消息、错误码和外部服务依赖。

### 7.8 第七章 页面与交互设计

- 移动端首页、AI 助手、画像雷达、会议、考试和资源卡片。
- Web 端知识库、题库、试卷、模型和智能体管理。
- 流式输出、生成进度、错误恢复、资源下载和历史会话。
- 运行截图优先；静态设计稿必须标注“界面设计稿”。
- 不使用 HBuilderX 操作截图冒充产品运行截图。

### 7.9 第八章 测试与验证

- 建立需求—设计—接口—测试追踪矩阵。
- 功能测试覆盖 AI 助手、画像、会议、知识库、题库、试卷和考试。
- 异常测试覆盖模型失败、MaxKB 超时、Redis 不可用、SSE 断开、版本冲突和预览失效。
- 当前 Java 报告为 324 项、0 failure、1 error、1 skipped；错误源于本地数据库不存在，不写成全量通过。
- Python 缓存记录不能作为正式通过率；仅引用能够重现的测试命令和新鲜结果。
- 试卷视觉链路可引用真实渲染和像素一致性验证，但必须注明覆盖范围。
- 未执行的性能、真机、渗透和生产端到端测试列入验证缺口，不编造指标。

### 7.10 第九章 安装部署与使用

- 软件与硬件环境。
- MySQL 8、Redis 7 和配置准备。
- Java 21 / Spring Boot 启动。
- Python FastAPI AI 服务单独启动。
- React Web 构建和 Nginx 部署。
- uni-app 使用 HBuilderX 构建运行。
- 外部服务只描述配置项名称，不复制真实值。
- 明确当前 AI 服务尚未纳入 Compose 和 CI 镜像。

### 7.11 第十章与附录

- 总结项目成果和赛题匹配。
- 说明考试反馈尚未自动进入画像、学习路径独立闭环仍在补齐等限制。
- 安全改进包括密码 BCrypt/Argon2、密钥环境变量化、WebSocket Origin 白名单和限流审计。
- 开源依赖列出名称、版本、来源和许可证核查状态，不宣称已完成全部许可证审计。
- AI Coding 说明：项目使用 OmX 辅助需求拆解、设计记录、代码实施和测试复核，最终结果由项目成员审阅并负责。
- 参考文献统一按 GB/T 7714 风格整理。
- 工程证据索引列出关键源码和文档相对路径，不暴露本地绝对路径。

## 12. 制作与验证流程

1. 提取当前仓库事实并生成内容底稿。
2. 绘制统一风格的架构图和流程图。
3. 使用 `python-docx` 和显式 OOXML 样式生成 DOCX。
4. 创建真实 Word 标题层级、目录、页码、图表编号和表格几何。
5. 渲染 DOCX 为逐页 PNG 和 PDF。
6. 逐页检查全部页面，修复裁切、重叠、表格跨页、图注、字体和空白。
7. 对最终 PDF 再次逐页渲染检查。
8. 执行占位符、编号、术语、敏感信息和事实边界扫描。
9. 只交付最终 DOCX 和 PDF。
